# 离线事件序列修复台

一个完全在浏览器本地运行的 NDJSON 事件序列修复工具。技术栈：**TypeScript + Vite + React**。

粘贴每行包含 `stream`、`sequence`、`payload` 的 NDJSON，为每条流设置起始序号后：

- **重复折叠**：同流、同序号、载荷按 JSON 结构深比较相同的事件自动折叠为一条；
- **冲突标记**：同流、同序号但载荷结构不同 → 标为冲突，列出全部候选版本（标注各自出现的输入行与重复次数）；
- **阻断规则**：缺号，或存在未裁决冲突，会阻断该位置**之后的所有事件**；
- **即时重算**：选择一个冲突版本、撤销选择或修改起始序号，连续前缀立即重新计算；
- **修复方案导入 / 导出**：将各流起始序号与冲突裁决导出为可移植 JSON（含版本与数据指纹），可在同一份数据（允许行序不同）上一键导入恢复；
- **导出**：仅导出每条流「已确认连续前缀」内的事件，可选择按流名+序号或全局序号+流名排序，输出 NDJSON。

所有解析、比较、裁决与导出均在浏览器内存中完成，**无任何网络请求，数据不会离开本机**。

## 输入格式

NDJSON，每行一个 JSON 对象：

```json
{"stream":"orders","sequence":1,"payload":{"id":"a","status":"created"}}
{"stream":"orders","sequence":2,"payload":{"id":"a","status":"paid"}}
```

- `stream`：字符串，流名；
- `sequence`：安全整数；
- `payload`：任意 JSON 值（对象、数组、基本类型均可）。

空行自动跳过；非法行会在解析结果中逐行报错并跳过，其余合法行正常处理。

## 一条命令启动（Docker）

需要已安装 Docker（含 Compose 插件）。在项目目录执行：

```bash
docker compose up --build -d
```

启动后在浏览器访问：

> **http://localhost:8080**

停止服务：

```bash
docker compose down
```

端口可在 `docker-compose.yml` 中修改（默认宿主机 `8080` → 容器 `80`）。

## 本地开发（不使用 Docker）

要求 Node.js 18+。

```bash
npm install
npm run dev        # 开发服务器，访问终端提示的地址（默认 http://localhost:5173）
npm run build      # 类型检查 + 生产构建，产物在 dist/
npm run preview    # 本地预览生产构建（默认 http://localhost:4173）
npm run verify     # 运行核心逻辑校验（解析/折叠/阻断/裁决/导出，共数十项断言）
```

## 使用说明

1. **粘贴数据**：将 NDJSON 粘贴到文本框，点击「解析并分析」（可先「载入示例」）。
2. **设置起始序号**：每条流卡片上可修改起始序号，默认为该流观测到的最小序号。
3. **处理缺口与冲突**：
   - 缺口区列出缺号，阻断点的缺号以红色高亮；
   - 冲突区并列展示候选载荷，选中单选按钮即裁决，点「撤销选择」恢复未裁决；
   - 「当前连续前缀」表格展示从起始序号起连续、已确认的事件。
4. **导入/导出修复方案**：在「3. 修复方案导入 / 导出」面板点击「下载修复方案（JSON）」保存当前起始序号与裁决；在另一份相同数据上点「从文件导入方案」即可恢复（格式见下节）。
5. **导出事件**：在底部选择排序方式，预览后「下载 NDJSON」或「复制」。导出内容严格限定为各流连续前缀。

## 修复方案（JSON）格式

方案是一个 **UTF-8 JSON 对象**（默认文件名 `repair-plan.json`），形如：

```json
{
  "version": 1,
  "fingerprint": "8f2e…（64 位十六进制 SHA-256）",
  "starts": {
    "orders": 1,
    "payments": 10
  },
  "resolutions": [
    {
      "stream": "orders",
      "sequence": 2,
      "candidateId": "{\"id\":\"a\",\"status\":\"paid\"}"
    }
  ]
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `version` | 方案格式版本，当前固定为 `1`；版本不符直接拒绝。 |
| `fingerprint` | **数据指纹**：对解析得到的合法事件多重集规范化后计算的 SHA-256（小写十六进制）。 |
| `starts` | 每个流的起始序号（安全整数），必须恰好覆盖当前数据的全部流。 |
| `resolutions` | 冲突裁决列表；未列出的冲突视为未裁决。 |
| `resolutions[].stream` / `sequence` | 冲突所在的流名与序号，且该序号在当前数据中必须确实是冲突。 |
| `resolutions[].candidateId` | 所选候选的**稳定标识**，即候选载荷对象键递归排序后的 JSON 文本（与界面候选一一对应）。 |

### 指纹口径（什么情况下能导入）

指纹按以下步骤计算，只依赖合法事件本身，与解析错误行无关：

1. 对每条合法事件规范化为 `[stream, sequence, 稳定序列化(payload)]` 再整体 JSON 编码；
   其中载荷的稳定序列化会对对象键递归排序，因此 JSON 键的书写顺序不影响指纹；
2. 将所有行按文本字典序排序后以换行连接（即对**多重集**规范化）；
3. 对连接结果计算 SHA-256。

因此：

- ✅ **输入行任意重排**（包括重复行位置变化、对象键书写顺序变化）→ 多重集不变 → 指纹一致，可以导入；
- ❌ 增删任一事件、修改流名/序号/载荷结构、或**某条事件的重复次数变化** → 指纹失配，整体拒绝。

### 导入的校验与应用

导入时严格按顺序校验，**任一项失败都会整体拒绝且不改变当前起始序号与裁决**，界面会显示具体原因：

1. 文件是合法 JSON 且为对象；
2. `version` 受支持（当前 `1`）；
3. `fingerprint` 为 64 位十六进制且与当前数据重算结果一致；
4. `starts` 是对象：流集合与当前数据完全一致（不缺、不多），每个起点是安全整数；
5. `resolutions` 是数组：每项的字段类型正确、引用的流/冲突序号存在、`candidateId` 在该冲突的候选中存在，且同一冲突没有重复裁决。

全部通过后才**一次性应用**起始序号与裁决，连续前缀随即自动重算。方案文件只在本机读取校验，不会上传。

### 裁决与阻断示例

流 `orders` 有序号 1、2、2、4，且两个序号 2 的载荷不同，起始序号为 1：

- 序号 1 直接进入前缀；
- 序号 2 冲突，未裁决时阻断，序号 4 即使存在也不可放行；
- 缺口列表显示缺号 3；
- 选定序号 2 的一个版本后，前缀推进到 2，随后因缺号 3 阻断；
- 导出只包含序号 1、2。

## 项目结构

```
.
├── Dockerfile              # 多阶段构建：node 构建 → nginx 静态托管
├── docker-compose.yml      # 一条命令启动，映射 8080:80
├── nginx.conf              # SPA 静态托管配置
├── index.html
├── package.json
├── tsconfig.json
├── vite.config.ts
├── scripts
│   └── verify.mjs         # 核心逻辑端到端断言（npm run verify）
└── src
    ├── main.tsx            # 入口
    ├── App.tsx             # 状态与页面编排
    ├── types.ts            # 领域类型
    ├── sample.ts           # 内置示例数据
    ├── styles.css
    ├── components
    │   └── StreamCard.tsx  # 单流：缺口 / 冲突候选 / 连续前缀
    └── lib
        ├── ndjson.ts       # NDJSON 解析与逐行校验
        ├── compare.ts      # JSON 结构深比较与稳定序列化
        ├── model.ts        # 按流/序号分组折叠、裁决与前缀分析
        ├── export.ts       # 连续前缀 NDJSON 导出与排序
        └── plan.ts         # 修复方案生成、SHA-256 数据指纹与导入校验
```
